# 면접 꼬리질문 10개

근거는 README와 `docs/issues/`에 적힌 것만 썼습니다. 수치는 문서에 있는 값 그대로이며(로컬 노트북, 서버 1대 기준), 문서에서 찾지 못한 것은 '근거 없음'으로 표시했습니다.

### 1. 재고 100개에 1,000명이 동시에 주문하면 어떻게 막았나요?
- **답변 요지**: 조회 후 차감이 아니라 `UPDATE ... SET stock = stock - ? WHERE stock >= ?` 한 문장으로 검사와 차감을 같이 합니다. 4가지 전략(NAIVE, PESSIMISTIC, OPTIMISTIC, ATOMIC_UPDATE)을 MySQL에서 같은 조건으로 재서 골랐습니다.
- **근거 파일**: `docs/issues/01-stock-concurrency.md`, README '재고 차감 전략 비교'
- **문서에 있는 수치**: 재고 2,000 / 주문 2,000건 / 동시 100, 2회 측정. NAIVE는 2,000개를 팔았는데 재고는 74개만 줄어듦. ATOMIC_UPDATE는 TPS 110/133, p99 2.4/1.9초, 정확.

### 2. 낙관적 락이 더 안전해 보이는데 왜 쓰지 않았나요?
- **답변 요지**: 한 행에 경합이 몰리면 충돌과 재시도가 늘어 재고가 남았는데도 실패합니다. 충돌 빈도에 따라 도구를 달리 썼습니다(재고는 원자적 UPDATE, 주문 상태 변경은 `@Version`).
- **근거 파일**: `docs/issues/01-stock-concurrency.md`, README '프로젝트 중점사항'
- **문서에 있는 수치**: OPTIMISTIC TPS 24/32, p99 14.0/6.2초, 주문의 35%가 재고가 남았는데 실패.

### 3. Redis 분산락은 왜 쓰지 않았나요?
- **답변 요지**: 재고가 DB 한 행에 있어 DB 락으로 원자성이 보장됩니다. 분산락은 DB 밖 자원을 조율할 때 쓰는 도구라고 판단했고, Redis는 캐시 무효화 전파와 요청 한도 카운터에만 썼습니다.
- **근거 파일**: `docs/issues/01-stock-concurrency.md#왜-redis-분산락을-쓰지-않았나`, README 기술 스택 표
- **문서에 있는 수치**: 근거 없음(설계 판단이며 Redis 분산락과의 비교 측정은 문서에 없음).

### 4. 락을 걸었는데도 1인 구매 제한이 뚫린 이유는?
- **답변 요지**: MySQL 기본 REPEATABLE READ에서는 락을 기다리는 사이 고정된 스냅샷을 읽습니다. 주문 생성 트랜잭션만 `READ COMMITTED`로 명시하고, 사용자 행 락으로 check-then-act를 막았습니다. 락 순서는 사용자 → 상품(id 오름차순)입니다.
- **근거 파일**: `docs/issues/02-purchase-limit.md`
- **문서에 있는 수치**: 제한 2개, 동시 요청 10건에서 4개 판매 → 정확히 2개 (README 표). H2는 통과하고 MySQL에서만 뚫렸다는 설명이 문서에 있음.

### 5. 따닥 클릭이나 네트워크 재전송으로 주문이 두 번 생기지 않게 어떻게 했나요?
- **답변 요지**: `Idempotency-Key` 헤더와 DB 유니크 제약(user + key)으로 막습니다. 애플리케이션 락이 아니라 DB 제약이라 서버가 여러 대여도 동작합니다. 프론트는 `inFlight` ref 가드로 요청 자체를 한 번만 보냅니다.
- **근거 파일**: `docs/issues/05-idempotency.md`, `frontend/src/pages/ProductDetailPage.tsx`, `frontend/e2e/e2e.mjs`
- **문서에 있는 수치**: 같은 멱등 키로 동시 주문 20건 → 정확히 1건. e2e: 결제 버튼 더블클릭 요청 1회, 모바일 구매 더블클릭 POST /api/orders 1회(이번 릴레이 최종 실행 PASS). 한계(IN_PROGRESS로 남은 키는 409)는 문서의 '남은 한계'에 있음.

### 6. PG 호출이 타임아웃 나면 어떻게 되나요? 결제됐는지 모르는 주문은요?
- **답변 요지**: PG 호출은 트랜잭션 밖에서 합니다(TX1 PAYING + REQUESTED 기록 → PG → TX2 반영). 타임아웃은 실패가 아니라 `UNKNOWN`이고 대사 배치가 PG를 조회해 확정합니다. 같은 `paymentKey`로 재시도해서 이중 결제를 막습니다.
- **근거 파일**: `docs/issues/06-payment-failure.md`, `PaymentReconciler`
- **문서에 있는 수치**: 장애 주입표: PG가 3초 지연 → 타임아웃(2초) 후 같은 키로 재시도, 결제 1건. PG 승인 직후 우리 DB 장애 → 대사가 APPROVED를 보고 PAID로 복구. 대사 주기 10초(코드 `reconcile-interval`).

### 7. 결제 확인 중(PAYING) 주문을 왜 만료·취소하지 않나요? 화면에서는 어떻게 보여주나요?
- **답변 요지**: 결과를 모르는 채 재고를 풀면 돈은 빠졌는데 상품은 다른 사람에게 팔립니다. 그래서 PAYING은 만료 스케줄러도 관리자 취소도 건드리지 않고 대사로만 빠져나갑니다. 화면은 보라 점선 박스와 '결제 확인 중'으로 보여주고 취소·재결제 버튼을 두지 않습니다.
- **근거 파일**: README '주문 상태 머신', `OrderStatus.java`, `OrderCancelService.java`, `frontend/src/pages/MyActivityPage.tsx`
- **문서에 있는 수치**: 근거 없음(규칙과 상태 전이 설명이며 수치 없음).

### 8. 재고는 언제 빼야 하나요? 결제하지 않고 떠나면요?
- **답변 요지**: 결제 완료 시점에 빼면 결제까지 한 사람에게 품절이라고 해야 합니다. 주문 시점에 선점하고 10분 TTL과 만료 스케줄러로 복구합니다.
- **근거 파일**: `docs/issues/07-stock-reservation.md`
- **문서에 있는 수치**: TTL 10분, 만료 스케줄러 5초 주기(README Mermaid, 코드 `expiry-interval`). 그 밖의 수치는 근거 없음.

### 9. 관리자가 재고를 조정했더니 16,602개가 된 일은 무엇이었나요?
- **답변 요지**: 재고를 덮어쓰는 방식에서 값이 어긋났습니다. 덮어쓰기 대신 `stock = stock + :delta` 증감으로 바꾸고, 상품 수정 시 재고가 되돌아가는 문제는 `@DynamicUpdate`로 변경된 컬럼만 UPDATE해서 고쳤습니다.
- **근거 파일**: `docs/issues/04-stock-lost-update.md`
- **문서에 있는 수치**: 한정 100개 상품의 재고가 16,602개로 불어남 → 증감 조정으로 실물 수와 일치(README 표).

### 10. 서버를 두 대로 늘리면 무엇이 깨지고 어떻게 고쳤나요?
- **답변 요지**: 서버 메모리에 기댄 것만 손봤습니다. 스케줄러는 ShedLock(JDBC)으로 한 서버에서만, 사용자 캐시는 커밋 후 삭제하고 Redis로 전파, 요청 한도는 공유 카운터입니다. Redis가 죽으면 요청 한도는 허용, 캐시 무효화는 TTL로 물러납니다. DB 이중화는 하지 않았습니다.
- **근거 파일**: `docs/issues/13-scale-out.md`, `docs/issues/09-auth.md`, README '한계와 다음 단계'
- **문서에 있는 수치**: 회원 정지 직후 서버 2대에서 최대 30초 통과 → 모든 서버에서 즉시 거부(README 표). 요청 한도는 분당 로그인 20(IP), 회원가입 10(IP), 주문 30(사용자). 캐시 TTL 30초.
