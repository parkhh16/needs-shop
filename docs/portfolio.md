# 포트폴리오·발표 소재집

PPT, 포트폴리오, 면접 답변, 서비스 소개를 만들 때 꺼내 쓰는 재료 모음이다. **모든 숫자는 측정으로 확인한 값이고 출처 문서가 붙어 있다.** 출처가 없는 숫자는 쓰지 않는다.

- 숫자를 쓸 때는 옆의 "조건"을 함께 말한다(대부분 로컬 노트북, 서버 1대, 시드 데이터 기준이라 절대값보다 같은 조건의 상대 비교다).
- 이미지 경로는 저장소 기준이다. 크기는 대부분 가로 800px 이하.
- 끝의 "쓰면 안 되는 표현"을 먼저 읽는다.

## 0. 한 줄 소개와 30초 피치

**한 줄**: 손님의 니즈(말하듯 쓴 검색어)를 상품과 잇고, 한정된 재고에 주문이 몰려도 재고와 돈이 어긋나지 않게 만든 쇼핑몰 주문·결제 시스템.

**30초**: "재고 100개짜리 상품에 1,000명이 동시에 주문하면 어떻게 될까?"에서 시작했습니다. 재고가 덜 줄어 없는 물건을 파는 문제, 따닥 클릭으로 주문이 두 번 생기는 문제, 결제는 됐는데 우리 서버가 모르는 문제를 직접 재현했습니다. 재고 차감 방법 4가지를 MySQL에서 같은 조건으로 재서 골랐고, 초과 판매 0건을 만들었습니다. 모든 개선은 "문제 재현 → 원인 → 해결 → 수치"로 문서에 남겼습니다.

**이름의 뜻** (README 도입부): 손님이 찾는 것(니즈)을 검색어로 받아 상품과 잇고, 못 찾은 검색어는 판매자에게 등록 추천으로 돌려준다. 그 니즈가 한정 재고 앞에서도 초과 판매나 이중 결제 없이 충족되게 한다.

## 1. 면접 핵심: 재고와 돈 (백엔드)

### 1-1. 재고 차감 4가지 전략을 실측해서 골랐다

- **메시지**: "더 안전해 보이는 것"이 아니라 같은 조건에서 재서 골랐다.
- **수치** (MySQL 8, 재고 2,000 / 주문 2,000 / 동시 100, 2회 측정):

| 전략 | TPS | p99 | 결과 |
|---|---|---|---|
| 락 없음 | 106 / 137 | 3.8 / 2.4초 | 2,000개를 팔았는데 재고는 **74개만 줄어듦** |
| 비관적 락 | 98 / 126 | 3.2 / 2.0초 | 정확 |
| 낙관적 락 | **24 / 32** | **14.0 / 6.2초** | **35%가 재고가 남았는데 실패** |
| **원자적 UPDATE (채택)** | **110 / 133** | **2.4 / 1.9초** | 정확, 초과 판매 0건 |

- **근거**: [이슈 01](issues/01-stock-concurrency.md), README "재고 차감 전략 비교"
- **시각 자료**: [stock-strategies.png](portfolio/stock-strategies.png) (TPS와 p99를 두 패널로 나눔. 제목은 "정확한 전략 중 가장 빠름": 2회 측정에서는 락 없음이 137로 더 빨랐다)

### 1-2. 측정이 틀렸다는 걸 발견하고 다시 쟀다

- **메시지**: 첫 측정의 결론("원자적 UPDATE가 55% 빠르다")이 다시 재니 뒤집혔다. 원인은 JVM 워밍업, 그리고 2,000건 중 1,900건이 품절로 바로 끝나 **경합을 거의 재지 못한 것**. 재고를 요청 수만큼 늘리고, 워밍업 후, 두 번, MySQL에서 다시 쟀다.
- **근거**: [이슈 01 "측정 설계를 다시 한 이야기"](issues/01-stock-concurrency.md#측정-설계를-다시-한-이야기)
- **쓰는 곳**: "실패 경험" 질문. 숫자보다 측정을 의심한 태도가 핵심.

### 1-3. 락을 걸었는데도 1인 구매 제한이 뚫렸다

- **메시지**: H2에서는 통과, MySQL에서만 터졌다. 기본 격리 수준(REPEATABLE READ)이 락을 기다리는 동안 옛 스냅샷을 읽었기 때문. 주문 생성만 `READ COMMITTED`로 명시.
- **수치**: 1인 2개 제한, 동시 요청 10건 → 수정 전 **4개 판매**, 수정 후 정확히 **2개**.
- **근거**: [이슈 02](issues/02-purchase-limit.md). 그래서 CI가 같은 테스트를 MySQL(Testcontainers)에서도 돌린다.

### 1-4. 따닥 클릭과 재전송: 멱등 키 + DB 유니크 제약

- **수치**: 같은 키로 동시 주문 20건 → **주문 1건, 재고 1개 차감**. 화면에서는 결제 버튼 더블클릭 시 결제 요청 1회(e2e). 같은 아이디로 동시 가입 10명 → 정확히 1명.
- **메시지**: 서버 메모리 락이 아니라 DB 제약이라 서버가 여러 대여도 동작한다.
- **근거**: [이슈 05](issues/05-idempotency.md), [이슈 09](issues/09-auth.md)
- **남은 한계(정직하게)**: 처리 중 상태로 서버가 죽은 키는 409로 남는다. 화면의 결제하기 버튼 가드와 멱등 키 재사용은 [backlog D](design/backlog.md)에 미해결로 있다.

### 1-5. 결제(PG) 장애: 타임아웃은 실패가 아니라 "모름"

- **메시지**: 외부 결제는 트랜잭션 밖에서 부르고, 결과를 모르면 `UNKNOWN`으로 둔 채 재고를 풀지 않는다. 대사 배치가 PG에 물어 확정한다.
- **장애 주입 결과**:

| 장애 | 결과 |
|---|---|
| PG가 승인 후 3초 지연 (타임아웃 2초) | 같은 결제 키로 재시도 → **결제 1건, 이중 결제 없음** |
| PG 5xx 지속 | 재시도 3회 후 UNKNOWN → 대사가 "PG에 기록 없음" 확인 → 재결제 가능 |
| **PG 승인 직후 우리 DB 장애** | **대사가 PG 조회로 PAID 자동 복구** |

- **찾은 버그**: 리팩토링 중 거절된 결제를 승인으로 오판할 뻔한 버그를 발견. HTTP 상태 코드가 아니라 응답 본문의 결제 상태로 판단하게 고침.
- **근거**: [이슈 06](issues/06-payment-failure.md)
- **시각 자료**: [내 활동 주문 상태 화면](design/shots/relay-n3/after/me-orders.pc.light.png) (결제 확인 중은 보라 점선, 취소·재결제 버튼 없음. 상태는 모의 응답으로 띄운 화면)

### 1-6. 재고가 100개에서 16,602개가 됐다

- **메시지**: 관리자 재고 조정이 덮어쓰기라 값이 어긋났다. 재고는 덮어쓰지 않고 `stock = stock + delta`로 증감하고, 상품 수정 시 재고가 되돌아가는 문제는 `@DynamicUpdate`로 막았다.
- **근거**: [이슈 04](issues/04-stock-lost-update.md)

### 1-7. 조회 성능

- **수치**: 주문 20건 목록 **22 → 3 쿼리** (N+1 제거), 내 주문 목록이 읽는 행 **994 → 10** (복합 인덱스, MySQL `EXPLAIN ANALYZE`).
- **근거**: [이슈 08](issues/08-query-performance.md)

## 2. 대규모를 대비한 것

"트래픽이 늘면?"에 대한 답. 실제 대규모 트래픽은 없었으므로 **"대비한 구조와 그걸 확인한 방법"**으로 말한다. 구성도: [server-architecture.png](portfolio/server-architecture.png)

| 대비 | 어떻게 | 확인한 것 | 근거 |
|---|---|---|---|
| 서버 여러 대 | 정합성은 DB가 지키고, 서버 메모리에 기댄 것만 손봄 | Docker Compose로 앱 2대 + Caddy, CI가 PR마다 띄워 스모크 테스트 | [이슈 13](issues/13-scale-out.md) |
| 스케줄러 중복 | ShedLock(DB 락)으로 한 서버만 실행 | 두 서버 동시 시작 시 한 서버만 실행 (`ClusterLockTest`) | 이슈 13 |
| 정지한 회원 즉시 차단 | 커밋 후 캐시 삭제 + Redis Pub/Sub 전파 | 서버 2대에서 **최대 30초 통과 → 즉시 거부**. 스모크: 캐시를 채운 뒤 정지하면 이어지는 6번 모두 403 | 이슈 13, [이슈 09](issues/09-auth.md) |
| 요청 한도 | Redis 공유 카운터. Redis가 죽으면 허용으로 물러남 | 같은 IP 로그인 25번 → 한도를 넘는 순간부터 429 | 이슈 13 |
| 로그 때문에 주문이 느려지지 않게 | 메모리 큐 + 300ms 배치 INSERT | 큐가 가득 차면(DB 장애 등) 로그를 버리고 버린 개수만 대시보드에 표시. 로그 때문에 주문이 실패하지 않는 설계 | [이슈 10](issues/10-activity-log.md) |
| 외부 결제 지연이 DB로 번지지 않게 | PG 호출을 트랜잭션 밖으로 | 장애 주입 표 (1-5) | 이슈 06 |
| 안전하지 않은 설정으로 운영 서버가 뜨지 않게 | `ProductionGuard`: 데모 키, `admin/admin`, H2, 개발 도구가 남으면 기동 중단 | 항목별 검출 테스트 | [이슈 12](issues/12-production-guard.md) |
| 요청 하나 추적 | traceId를 서버 로그, 에러 응답, `X-Trace-Id` 헤더, 활동 로그에 같은 값으로 | 사용자가 에러 화면의 traceId를 알려주면 그 요청을 끝까지 찾음. 활동 로그 표에 traceId 열 | 이슈 10 |

**다음 단계로 말할 것** (README "한계와 다음 단계"): DB 한 대 → 한계에 오면 Redis `DECR`로 재고 게이트를 앞단에, 결제 반영은 Outbox + 메시지 큐로. **하지 않은 것을 했다고 말하지 않는다.**

## 3. AI 사용과 개선

### 3-1. AI를 손님이 기다리는 곳에서 뺐다

- **메시지**: 검색마다 LLM(Gemini)을 불렀더니 응답이 한 번에 **7.5초**(세 번 재서 7.4~7.6초)여서, 타임아웃 5초에 걸려 모든 검색이 5초를 기다린 뒤 규칙으로 넘어갔다. 손님이 기다리는 경로에서 AI를 빼고, 기다림이 문제 되지 않는 곳(상품 등록 후 태그, 하루 한 번 등록 추천)으로 옮겼다.
- **근거**: [이슈 11 2절](issues/11-ai-search.md)
- **쓰는 곳**: "AI를 어디에 쓰나"보다 "어디에 안 쓰나"를 판단한 사례.

### 3-2. AI는 해석만, 사실은 코드가 확인

- **메시지**: 등록 추천에서 AI는 "물 튀어도 되는 스피커"와 "샤워할 때 듣는 스피커"를 "방수 스피커"로 묶는 뜻 해석만 한다. 횟수, 실제로 그런 상품이 있는지는 코드가 DB로 다시 확인한다. 실제 Gemini로 돌리며 **다섯 번** 고쳤다(예: AI가 "마이크"로 줄인 이름이 마우스 스펙의 "마이크로 스위치"와 맞아 저소음 마우스를 마이크로 착각).
- **근거**: 이슈 11 5절
- **시각 자료**: [admin-demand.png](portfolio/admin-demand.png) (AI 키가 없는 환경이라 "AI 정리"는 비어 있고 못 찾은 검색어 집계만 보인다. 검색 기록 53건은 시연용이라는 안내가 화면에 있다)

### 3-3. 검색 품질을 숫자로 관리했다

| 단계 | 정답만 나온 질의 (72개 중) | 무엇이 올렸나 |
|---|---|---|
| 처음 | 28 (39%) | |
| 검색 기본기 | 63 (88%) | **규칙 코드** +35: 띄어쓰기, 조사, 가격 표현, 오타 교정(자모 편집 거리), 상세 설명까지 찾기 |
| AI 태그 | 66 (92%) | **AI** +3: 상품 등록 때 손님이 쓸 말("가벼운", "fps")을 태그로 |
| 처음 보는 질의 32개 (정답을 먼저 커밋) | 27 (84%) | 92%가 평가셋에만 맞춘 숫자가 아닌지 확인 |

- "처음 보는 표현"(상황·느낌으로 쓴 질의 20개)만 보면 **1 → 13 → 15**개.
- **시각 자료**: [search-quality.png](portfolio/search-quality.png), 실제 검색 화면 [search-natural-language.png](portfolio/search-natural-language.png) ("손목 아픈 사람용 마우스" → 버티컬·트랙볼 마우스, "이렇게 이해했어요" 칩)
- **근거**: 이슈 11 6절, held-out 절. README 주요 결과 표.

### 3-4. 측정이 고친 걸 되돌리게 했다

- **메시지**: 처음 보는 질의의 실패를 고치기 전에 **또 다른 처음 보는 질의 31개를 먼저 커밋**하고 고쳤다. "맨 뒤 단어 필수" 규칙은 한 질의를 고쳤지만 이미 맞던 질의 4개를 0건으로 만들어(전체 119 → 117) **되돌렸다**. 남긴 수정도 새 질의에서는 26/31로 그대로여서 "단어 하나가 아니라 어휘 전체를 고쳐야 한다"는 결론을 얻었다.
- **근거**: 이슈 11 "고치고, 또 처음 보는 질의로 재기", 커밋 순서 `e3dc8c4` → `77b8114` → `6e670e0` → `57e5d67` (PR #20)
- **쓰는 곳**: 평가(eval) 설계, 과적합을 경계하는 태도. 하네스 엔지니어링 이야기의 실물.

### 3-5. AI 에이전트로 개발 흐름을 운영했다 (하네스 엔지니어링)

- **구조**: 역할과 수정 권한을 나눈 에이전트 9개(`.claude/agents/`). 리뷰어는 파일을 못 고치고, 테스터는 `src/test`만, 디자이너는 `docs/design`만 쓴다. 주문·재고·결제·인증을 바꾸면 리뷰어를 반드시 거친다(`CLAUDE.md`).
- **비용을 재고 규칙으로 바꿨다** ([LESSONS.md](LESSONS.md)): 메인 호출 1건이 약 17만 토큰, 한 세션 캐시 읽기 24.9M 중 메인이 63% → 에이전트는 라운드당 최대 6개, 포그라운드 기본, 끝나기 전에 커밋. 한 라운드가 토큰 11.3M을 쓰고도 눈에 보이는 변화가 없었던 경험 → 시작 전에 "눈에 보이는 변화" 기준을 적는 규칙.
- **측정 오류를 잡았다**: 시각 채점에서 홈이 6~7점이었는데, 지연 로딩 이미지가 캡처 때 안 불러와진 캡처 도구 문제였다. 도구를 고치고 전후를 다시 찍었다([history.md](design/history.md)).
- **사람이 판단한 지점**: 사이드바를 먼저 지운 에이전트에 "사이드바 없애버린겨?"라고 물은 뒤, 구조 요소는 먼저 묻는 규칙(LESSONS B2)을 만들고 PC 사이드바를 되살렸다.

## 8. PPT 구성 예

**3장 (5분)**: ① 문제와 30초 피치 (0장) ② 핵심 해결 3가지와 수치 (1-1, 1-4, 1-5) ③ 검증 방식과 한계 (2장, 7장). 이미 만든 3장 자료가 이 구성이다.

**8~10장 (15분)**: 표지(홈 이미지) → 문제 3가지 → 재고 전략 실측 그래프(1-1) → 측정을 다시 한 이야기(1-2) → 격리 수준(1-3) → 결제 장애(1-5) → 서버 2대(2장) → AI를 어디에 쓰고 안 쓰나(3-1, 3-2) → 평가로 관리한 검색 품질(3-3, 3-4) → 한계와 다음 단계.
